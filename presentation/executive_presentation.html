Executive Summary

ALL AUDIENCES

The Problem

Raw transactional CSV files from 8 datasets — customers, orders, products, sellers, payments, reviews, and geography — were siloed, inconsistent, and impossible to query for business decisions. No single source of truth existed.

Our Solution

Built a 4-stage automated ELT pipeline on Google BigQuery that validates, ingests, transforms, and tests 333 MB of raw data into a production-grade star schema — 10 analytics tables, always fresh, always tested.

Business Impact

Any analyst can now answer questions like "Which product categories drive the most revenue?" or "Which customers are at risk of churn?" with a single SQL query — in seconds, not days.

Bottom line: We turned 9 raw CSV files and 333 MB of data into a structured, validated, queryable analytics layer covering 99,441 orders, 100K+ customers, 32K products, and 3K sellers — with automated data quality gates at every step of the pipeline.

Data Coverage

~2 years of Brazilian e-commerce transactions from Olist, Brazil's largest marketplace platform (Kaggle dataset)

Time to Insight

Full pipeline runs end-to-end in under 2 minutes. A single command (./run_pipeline.sh) triggers all four stages with automatic failure detection.

Quality Guarantee

Two independent validation layers: 25+ pre-load expectations on raw files, and post-transform tests on every analytics table — zero bad data reaches dashboards.

Key Business Insights Enabled

BUSINESS

Customer Segmentation (RFM)

Every customer is automatically classified into actionable segments based on recency, frequency, and spend:

  • Champions — purchased within 90 days, 3+ orders, high spend
  • Loyal — purchased within 180 days, 2+ orders
  • At-Risk — haven't purchased in 90–365 days
  • Churned — no activity in over a year

Delivery Performance

Delivery date vs. estimated date tracked per order, enabling:

  • On-time delivery rate overall and by seller state
  • Average delivery days by region (identify logistics gaps)
  • Approval cycle time (find processing bottlenecks)
  • Carrier handoff delay tracking

Category Revenue Analysis

All 72 product categories mapped to 10 business-friendly groupings — Electronics, Fashion, Home, Health & Beauty, Art & Culture, Books, Toys & Games, Automotive, Food & Drink, Other. Revenue, order count, and average price queryable at any level.

Review Sentiment by Category

For every category with 50+ reviews, the platform exposes the positive review rate, average score, and sentiment breakdown. Directly actionable for product/supplier quality decisions and customer satisfaction benchmarking.

Geographic Intelligence

Orders, customers, and sellers all geocoded to Brazilian states and 5 macro-regions. Cross-regional shipping distances and seller-proximity analysis are supported.

Historical Trend Analysis

Full calendar dimension (5 years back / forward) with ISO weeks, holidays flag, and day-of-week attributes. Any metric can be trended monthly, quarterly, or year-over-year.

Installment Payment Patterns

Credit card installment usage tracked per order — number of installments, payment value, risk level. Enables credit exposure and cash-flow timing analysis.

Technology Stack

  • Google BigQuery — cloud data warehouse (US region)
  • dbt 1.10 — SQL transformation & testing framework
  • Meltano 4.0 — open-source ELT orchestration
  • Great Expectations 1.8 — data validation (ephemeral context)
  • Python 3.11 — runtime, environment management via Conda
  • run_pipeline.sh — single-command full pipeline execution

Why dbt?

SQL-first transformations with version control, modular dependencies, auto-generated documentation, and native BigQuery dialect support. Separates concern of "what" from "how" in each layer.

Why Meltano?

Open-source Singer-protocol ELT. Declarative YAML config, pluggable extractors and loaders. Storage Write API enables reliable, high-throughput bulk loads to BigQuery.

Why BigQuery?

Serverless, auto-scaling, pay-per-query. No infrastructure to manage. Handles the full 333 MB dataset in seconds. Integrates directly with Looker, Tableau, and Power BI.

Data Warehouse Design — Star Schema

TECHNICAL
Table Type SCD Grain Approx Rows Business Purpose
fct_orders Fact — 1 row per order ~99K Revenue, delivery performance, payment analysis
fct_order_items Fact — 1 row per line item ⭐ ~112K Most atomic — product, seller, category revenue
fct_product_reviews Fact — 1 row per review ~99K Sentiment, satisfaction, quality scoring
dim_date Dim Static 1 row per day ~3,650 Conformed calendar — shared across all facts
dim_geography Dim Static 1 row per zip prefix ~1,345 Conformed location — customers & sellers
dim_payment_type Dim Static 1 row per method 5 Payment channel, risk level, installment flag
dim_product_category Dim SCD Type 2 1 row per category version ~72 EN translation, category type grouping, history
dim_products Dim SCD Type 1 1 row per product ~32K Physical specs, category link, volume derived
dim_customers Dim SCD Type 2 1 row per customer version ~100K Address history, state, geography link
dim_sellers Dim SCD Type 1 1 row per seller ~3.6K Location, state, geography link

Conformed Dimensions

dim_date and dim_geography are shared across all fact tables — this ensures consistent metrics when comparing revenue over time or customers vs. sellers by region.

SCD Type 2 (History Tracking)

Customer and category records track history via valid_from_date, valid_to_date, is_current. Enables time-travel queries: "What were revenue figures on Jan 15, 2024?"

Surrogate Keys

All dimensions carry integer surrogate keys. Business keys (order_id, product_id) are preserved as degenerate dimensions in fact tables — insulating analytics from upstream changes.

Data Quality & Governance

TECHNICAL
🛡 Layer 1 — Pre-Load Validation (Great Expectations)
order_items — non-null keys, price ≥ 0, freight ≥ 0
order_payments — valid payment_type enum (5 values), value ≥ 0
orders — unique order_id, valid status enum (8 values)
order_reviews — review_score between 1–5
customers — non-null customer_id & unique customer identifier
products — non-null product_id & category name
sellers — non-null seller_id
Runs entirely in-memory. Exit code 1 blocks Meltano from loading bad data to BigQuery.
✅ Layer 2 — Post-Transform Tests (dbt test)
Uniqueness — surrogate keys on all 10 analytics tables
Not-Null — critical columns: order_id, customer_key, product_key, date_key
Accepted Values — order_status constrained to 8 known values
Referential integrity — fact → dimension key relationships
Calendar completeness — dim_date unique per calendar_date
Payment type uniqueness — dim_payment_type natural key
Pipeline fails at this stage if any test fails — dashboards never show invalid data.
Design principle: The pipeline is fail-fast. A single failed expectation or dbt test stops the entire run and returns a non-zero exit code. No partial loads, no silent failures. Every table in the analytics schema has been validated end-to-end before it is queryable.

SAFE_CAST Throughout

All staging models use BigQuery's SAFE_CAST instead of hard casts — malformed values return NULL rather than crashing the pipeline.

Ephemeral Validation Context

Great Expectations runs fully in-memory — no stale configuration files on disk. Every run re-derives expectations from source code.

Seed Reference Data

Product category translations loaded via dbt seed — version-controlled static data, not dependent on Meltano load state.

Risks & Mitigations

ALL AUDIENCES
Risk Severity Current State Mitigation / Path Forward
Historical Dataset Only
Data is static (Oct 2021 snapshot). No live feed.		 Medium All analysis is retrospective; cannot support real-time ops decisions Connect a live Olist or similar source API via Meltano tap. Add incremental load strategy to dbt models.
Full-Reload Only (No Incrementals)
Every run reprocesses all data.		 Medium Acceptable for 333 MB. Will become costly at 10× scale or with BigQuery on-demand pricing. Implement dbt incremental models for fact tables using is_incremental() + watermark on order date.
Incomplete SCD Type 2 for Customers
Snapshot defined but not wired to dim_customers.		 Low Customer address history not yet captured. Current data is still correct. Wire the existing dbt snapshot to dim_customers model in next sprint. Snapshot infrastructure already exists.
Hardcoded Credentials Path
Service account JSON path in meltano.yml.		 Low Acceptable for academic/dev environment. Not suitable for shared or CI/CD deployment. Move to environment variables or Google Secret Manager. Parameterise via Meltano environment config.
Missing Attributes in Dimensions
is_holiday, regional_sales_tier, seller_onboarded_date are NULL.		 Low Cosmetic gaps — does not affect accuracy of revenue, delivery, or sentiment metrics. Brazil holiday calendar can be seeded. Sales tier derives from aggregated fct_order_items. Seller date from first order.
Honest assessment: This platform is production-ready for analytical workloads on the Olist dataset as-is. The gaps above are enhancements, not defects — every metric documented in this presentation is fully queryable today.
